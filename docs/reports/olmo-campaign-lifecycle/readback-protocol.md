# Fixed-generation checkpoint readback comparison

This opt-in CPU-only diagnostic compares peak host memory and elapsed time for one complete retained checkpoint readback. It does not change the frozen retainer, upload data, load tensors, run GPUs or qualify a new checkpoint policy. Root schedules it after concurrent checkpoint transfers finish.

Authority is the completed `base-reference-01/report.json`, SHA256 `6e945cf271c1791a3dcb4e71f2f481e8389bb59477dad1f78097db2a23563d25`, its unique update-1 local receipt and the matching verified published receipt. The exact state generation is `1790680957093316`, length `14154933413`, SHA256 `5ed5a23f7d9f2753e76bbf95ed45797f8ddafb30f82ca7b276dc8e98ce2203e5`, MD5 `oNJ04OABVkvef0iAR49pVA==`. Children recheck remote generation, size, MD5, SHA256 metadata and absent content encoding before downloading.

One pair runs in order: `download_as_bytes`, then `download_to_file` into a counting SHA256/MD5 sink. Each arm uses a fresh Python subprocess and the same generation precondition, default non-single-shot SDK download and bounded retry policy. No whole payload is retained in the streaming arm. Sink writes either accept a complete chunk or fail; overflow, seek/transcoding, final truncation and digest mismatches fail closed. Ordinary range retries append from bytes already accepted; focused tests exercise the installed SDK continuation behavior with small fake responses. Final independent full hashes remain mandatory because SDK checksum handling differs for partial responses.

Each child records metadata time separately, then times the complete download plus required full size/SHA256/MD5 verification. The bytes arm separately records transfer-return and post-download hashing durations; streaming interleaves network and hashing and does not claim that separation. Both compute MD5 even though the old retainer's post-download Python check only computes SHA256. SDK checksum verification remains enabled. Linux `ru_maxrss` before/after (KiB), the increase in high-water RSS and current RSS before/after are reported; a fresh process avoids inherited earlier high-water marks. No tensor deserialization or local model copy occurs.

Parent and child source/environment records pin this helper, focused tests, this protocol, existing retainer/tracker and installed SDK source/version. Parent starts one online W&B run in `taylorbollman/pretrained-fbt-rt-nextlat` and logs the small result for each method. Parent persists each child observation before interpretation; a failed arm prevents a success claim. Timeout: 300 seconds per child, 330-second subprocess bound, 900-second outer scheduling bound. No automatic benchmark repetitions or retries of whole child runs.

The fixed order, single pair, server/network cache, credentials/session setup, host contention and SDK checksum work are qualifications. Metadata/client setup lies outside the measured transfer interval. A memory reduction can motivate a separately reviewed implementation change; a speed difference in one pair does not establish a general throughput improvement. Upload performance, end-to-end checkpoint pause, retry fault tolerance under real network failure and asynchronous retention are outside scope.
