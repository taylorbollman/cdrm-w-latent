# Final evaluation procedure review

Independent read-only audit on 2026-09-07, followed by an external stdlib planning helper. No GPU workload, checkpoint deserialization, final-data generation, or final-data inspection was performed. This is an operational review, not evidence of final-set performance.

The current native evaluation path is suitable for the selected six-block comparison. It reconstructs the original model/configuration and requires exact training-identity equality before loading the checkpoint and final split. It runs FP32 evaluation with math SDPA and no optimizer updates. Its saved output contains aggregate native/answer loss sums, target/correct/example/exact counts, derived metrics, and checkpoint/data/source identity. It does **not** save predictions or per-example correctness arrays.

Use the following sequence:

1. Freeze the setting and common endpoint across SEQ/CDRM and seeds 0/1 before model final-set access. Resolve continuation under the recorded cost policy, which considers E50, E45 and the retained E25 endpoint. For each member, require a completed report at that endpoint, with no partial epoch. A screening run may supply the compatible SEQ baseline; evaluate it using `--run-purpose comparison` because screening final evaluation is prohibited.
2. Select the endpoint from `roles.milestones[endpoint]`. Select best-development by the **lowest answer CE through that endpoint**, including epoch 0; strict improvement means the earliest tied minimum wins. Do not select by accuracy or use a later continuation's best-development role for an earlier endpoint. Continuation uses a new directory and preserves parent artifacts. Verify file hashes, then retain a logical role map even when endpoint and best-development share one checkpoint SHA.
3. Prepare an immutable evaluation plan before adding final data. The helper checks the complete cohort, report/ledger consistency, current source hashes, frozen train/dev/permutation file hashes, common configuration and ordered training indices, same-seed initial backbone identity, and selected checkpoint hashes/sizes. It deduplicates evaluations by artifact SHA within each topology/seed. It deliberately does not deserialize checkpoint payloads; the native evaluator performs strict identity and model-state loading later.
4. Append only the selected setting's final split through `cdrm_prepare_mad.py --setting copy-v16-t256-k96 --splits final --append-splits`, using the original data directory and frozen source. The append API checks the original setting, sizes, split seeds, shuffle seed, adapter/preparer hashes and retained files. It creates final split files and `manifest.added-final.json`; it leaves the original `manifest.json`, train/dev split files/manifests and epoch permutations unchanged. Recheck all recorded existing-file hashes after append, and record the new final manifest/hash separately.
5. Pass each plan entry's `label` and `argv` array to the existing `execution/run-final.py`. Use a fresh output directory for each unique checkpoint. Preserve the role mapping when one evaluation serves both roles. Require successful reports with the expected checkpoint SHA, original training identity and common final dataset identity. Report metric counts, not nonexistent prediction artifacts.

  --decision PATH_TO_FROZEN_DECISION --output PATH_TO_NEW_FINAL_EVALUATION_PLAN

The decision schema is `cdrm-final-endpoint-decision-v1`, with `endpoint_choice_frozen: true`, `final_access_authorized: true`, `setting`, `task`, `preset`, `endpoint_epochs`, `seeds: [0,1]`, `topologies: ["seq","cdrm"]`, `data_root`, `evaluation_output_root`, and four `cohort` entries containing `seed`, `topology`, `report_path` and `report_sha256`. The resulting plan records the decision/helper/input hashes, role mapping, expected final split identity, and shell-safe argument arrays; it refuses incomplete cohorts, changed inputs, existing final files and an existing plan output.

The usage guide's final command omits `--monitor-every`; its default of 100 matches the current selected SEQ/CDRM identities, so there is no current mismatch. The helper nevertheless passes it explicitly because it is part of computational identity even during evaluation. Other explicit identity arguments are topology, preset, task, original data root, physical batch, seed and shuffle seed.
